# Cerno — Build Specification

> **Cerno** comes from the Latin *cernō*: to discern, perceive, distinguish, or decide.  
> The name reflects the product's job: separating what an AI coding agent *claims* it did from what the available evidence can actually establish.


## Mission

Build **Cerno**, a local-first autonomous verification agent for **Claude Code**.

Cerno exists because AI coding agents are increasingly capable of changing large parts of a software project faster than a human developer can manually verify those changes.

Claude Code may say that a task is complete, tests pass, and existing behavior was preserved. Cerno must independently investigate whether the resulting codebase actually satisfies what the developer originally asked for.

The core product idea is:

> **Claude Code writes the software. Cerno determines whether the evidence shows it still matches the developer's intent.**

Cerno is **not** another coding agent, code generator, PR reviewer, static analyzer, or generic AI chat interface.

It is a **verification layer around Claude Code**.

The key relationship Cerno maintains is:

```text
Developer Intent
      ↓
Claude Code Actions
      ↓
Codebase Changes
      ↓
Runtime Evidence
      ↓
Evidence-backed Verdict
```

The product must answer:

1. What did the developer actually ask Claude Code to do?
2. What requirements, invariants, constraints, and prohibitions are implied by that request?
3. What did Claude Code actually touch or change?
4. Which changes are relevant to each requirement?
5. What parts of the surrounding codebase could those changes affect?
6. What deterministic or runtime evidence can verify the requirement?
7. If deterministic evidence is insufficient, what additional evidence should the AI verification agent investigate?
8. Is each requirement **VERIFIED**, **LIKELY**, **UNCERTAIN**, or **VIOLATED**?
9. What concrete evidence supports that conclusion?
10. How much repository context and model usage did Cerno avoid by investigating selectively instead of sending the whole repository to an LLM?

# Product Philosophy

## 1. Haiku is the reasoning agent

Use **Claude Haiku 4.5** as the default verification model through the Anthropic API.

The model must be configurable through an environment variable and adapter so it can be replaced later without changing the verification architecture.

Default:

```text
CERNO_MODEL=claude-haiku-4-5-20251001
```

Haiku is responsible for:

- turning natural-language developer intent into structured requirements;
- deciding what evidence is still needed for a requirement;
- choosing among Cerno's available verification tools;
- interpreting semantic relationships between intent and code;
- resolving conflicting evidence;
- deciding when enough evidence has been collected;
- producing concise evidence-backed explanations.

Haiku is **not** responsible for discovering the repository by blindly reading everything.

The deterministic layer must make the model's job easier.

## 2. Algorithms are the agent's senses

Git, Tree-sitter, code search, dependency traversal, Claude Code telemetry, and test runners are tools available to the verification agent.

They are not substitutes for the agent.

The model reasons.

The tools observe.

The verification engine combines both.

## 3. Never send the entire repository to the model

The central cost and architecture principle is:

> **Give the reasoning model the smallest amount of context necessary to reach a defensible conclusion.**

Cerno must perform context reduction before semantic reasoning.

Prefer:

```text
requirement
→ changed files
→ changed symbols
→ nearby callers/imports/references
→ relevant tests
→ small evidence packet
→ model reasoning
```

Never default to:

```text
whole repository
→ model
```

## 4. Evidence beats confidence

A model saying "this looks correct" is not verification.

Every verdict must contain evidence.

Prefer evidence in this order:

```text
Level 4 — targeted runtime behavior / acceptance test
Level 3 — existing automated test or build result
Level 2 — deterministic static/structural evidence
Level 1 — semantic inference from relevant code
Level 0 — insufficient evidence
```

A requirement may only be marked **VERIFIED** when there is deterministic or runtime evidence strong enough to prove it.

Semantic reasoning alone may produce **LIKELY**, **UNCERTAIN**, or **VIOLATED**, but not VERIFIED.

## 5. Uncertainty is a valid answer

Do not force certainty.

If Cerno cannot establish a claim within its investigation budget, return:

```text
UNCERTAIN
```

and explain what evidence is missing.

> Uncertainty is cheaper and safer than hallucinated certainty.

# Scope

Build a polished hackathon-ready MVP that works end-to-end.

### V1 must support

- Claude Code as the coding agent being observed.
- Local Git repositories.
- JavaScript / TypeScript / TSX repositories as the primary code-analysis target.
- Python source parsing as a secondary target if it can be added cleanly.
- Claude Code prompt/session capture.
- Git working-tree change analysis.
- Changed-symbol extraction using Tree-sitter.
- Lightweight import/call/reference relationships.
- Requirement-specific evidence retrieval.
- A bounded Haiku verification-agent loop with custom tools.
- Deterministic verification checks.
- Safe runtime checks.
- SQLite-backed state.
- A FastAPI backend.
- A React/Vite/TypeScript dashboard.
- A reproducible demo fixture in addition to live Claude Code integration.

### V1 is OBSERVE mode

Cerno observes and verifies.

It **does not block Claude Code actions** in the MVP.

Design the internal architecture so future modes can be added:

```text
OBSERVE → report only
GUARD   → warn during risky actions
ENFORCE → block explicitly forbidden actions
```

Do not implement Guard or Enforce unless the full MVP is already stable.

# Non-goals

Do not build:

- a replacement for Claude Code;
- an IDE;
- a VS Code extension for V1;
- a general PR reviewer;
- autonomous code repair;
- a multi-agent Claude-vs-Codex system;
- a vector database;
- a graph database;
- a cloud-first architecture;
- a large RAG framework;
- a generic arbitrary-shell AI agent;
- a full program-analysis compiler;
- support for every programming language.

Do not add LangChain, LangGraph, CrewAI, AutoGen, Pinecone, Weaviate, Qdrant, Neo4j, Redis, Celery, Kafka, Kubernetes, or Supabase unless there is a genuinely unavoidable reason.

There should not be one.

# 1. Claude Code Capture Layer

Integrate with Claude Code through project-level hooks in:

```text
.claude/settings.json
```

`cerno init` must safely merge Cerno hooks with existing settings.

Never overwrite existing user hooks.

Create a timestamped backup before modifying the settings file.

Capture at least:

```text
SessionStart
UserPromptSubmit
PreToolUse
PostToolUse
PostToolUseFailure
Stop
StopFailure
```

Prioritize `Edit`, `Write`, and `Bash` activity for tool telemetry.

Claude can modify files through shell commands, so do **not** assume Edit/Write hooks capture every file mutation.

At `Stop`, always rescan the working tree with Git.

Store raw hook payloads as JSONL.

Each normalized event should resemble:

```json
{
  "event_id": "uuid",
  "session_id": "string",
  "event_type": "post_tool_use",
  "timestamp": "ISO-8601",
  "tool_name": "Edit",
  "path": "src/auth/session.ts",
  "command": null,
  "success": true,
  "raw_payload_path": "..."
}
```

Where available, record the Claude session transcript path provided by hook metadata.

Do not duplicate the entire Claude transcript into model context.

Treat the transcript as an evidence source that can be queried selectively.

# 3. Intent Compiler

When the user submits the main task prompt, send it to Haiku using a strict structured-output schema.

Compile natural language into an **Intent Contract**.

Required model:

```python
class Requirement(BaseModel):
    id: str
    text: str
    type: Literal[
        "feature",
        "invariant",
        "constraint",
        "prohibition",
        "security",
        "performance",
        "verification",
        "other"
    ]
    priority: Literal["critical", "high", "normal"]
    explicit: bool
    verification_hint: str | None
```

And:

```python
class IntentContract(BaseModel):
    task_summary: str
    requirements: list[Requirement]
    protected_areas: list[str]
    explicit_acceptance_criteria: list[str]
```

Example:

Developer:

```text
Add GitHub OAuth.
Preserve existing email/password login.
Use the current User model.
Do not create a new database table.
Keep secrets in environment variables.
Add tests.
```

Expected contract:

```json
{
  "task_summary": "Add GitHub OAuth",
  "requirements": [
    {
      "id": "R1",
      "type": "feature",
      "text": "Users can authenticate with GitHub",
      "priority": "critical",
      "explicit": true
    },
    {
      "id": "R2",
      "type": "invariant",
      "text": "Existing email/password login continues to work",
      "priority": "critical",
      "explicit": true
    },
    {
      "id": "R3",
      "type": "constraint",
      "text": "Use the existing User model",
      "priority": "high",
      "explicit": true
    },
    {
      "id": "R4",
      "type": "prohibition",
      "text": "Do not create another database table",
      "priority": "critical",
      "explicit": true
    }
  ]
}
```

Do not over-expand vague prompts into dozens of invented requirements.

Prefer a small set of meaningful, testable statements.

# 6. Lightweight Impact Graph

Use plain Python adjacency maps.

Do not use Neo4j.

Represent relationships such as:

```text
file imports file
symbol calls symbol
test references symbol
changed symbol affects caller
```

Example:

```text
login()
   ↓
authenticatePassword()
   ↓
createSession()
      ↑
oauthCallback()
```

Implement bounded BFS/DFS.

Default graph expansion depth:

```text
2
```

Allow the verification agent to request one additional expansion when evidence remains insufficient.

Never recursively load the entire repository merely because a symbol is highly connected.

# 7. Evidence Retrieval Algorithm

This subsystem is critical.

For every requirement:

### Step A — deterministic classification

Determine whether the requirement can be answered directly from structured evidence.

Examples:

```text
"Do not change database migrations"
→ inspect migration/schema paths

"Do not add dependencies"
→ compare package manifests

"Add tests"
→ detect relevant test changes + test execution

"Do not modify auth files"
→ changed-file comparison

"Build must pass"
→ execute build
```

If the requirement can be conclusively verified or violated, do not spend a semantic reasoning call unnecessarily.

### Step B — identify candidate evidence

Start with:

```text
changed files
changed symbols
requirement keywords
symbol names
file names
test names
Claude tool events
```

Then expand through the impact graph.

### Step C — rank evidence

Use a transparent heuristic score based on factors such as:

```text
direct diff relevance
symbol-name/keyword relevance
graph distance
test relationship
Claude tool-event relevance
file risk
```

Keep the exact scoring simple and configurable.

Do not pretend the score is probabilistic truth.

### Step D — construct a compact evidence packet

The packet passed to Haiku should contain only what is necessary.

Example:

```text
REQUIREMENT R2
Existing password authentication must continue working.

RELEVANT CHANGES
src/auth/session.ts:createSession

DIFF
- expiresIn: "24h"
+ expiresIn: "30m"

DEPENDENCY PATHS
login
→ authenticatePassword
→ createSession

TEST EVIDENCE
password-login.spec.ts: PASS

AGENT EVENTS
Claude edited src/auth/session.ts after adding reset-token logic.

OPEN QUESTION
Does the session lifetime change violate the requirement?
```

# 8. Verification Agent

Implement Cerno's reasoning core as a bounded tool-using Claude agent.

Use the Anthropic Python SDK directly.

Do not use LangChain/LangGraph.

The model gets a system prompt explaining:

```text
You are Cerno, an evidence-first software verification agent.

Your job is not to approve code by default.
Your job is to determine whether one developer requirement is satisfied.

Investigate before concluding.

Prefer deterministic and runtime evidence over semantic inference.
Request only the smallest additional evidence needed.
Never assume a test passes unless tool output proves it.
Never assume unchanged behavior merely because existing tests pass.
Do not inspect unrelated code.
Do not call tools once the evidence is sufficient.
Return UNCERTAIN when the available evidence cannot establish a conclusion.
Every conclusion must cite evidence IDs supplied by tools.
```

Use custom client tools with strict schemas.

Implement approximately these tools:

```text
get_requirement(requirement_id)
get_changed_files()
get_file_diff(path, max_lines)
get_changed_symbols(path)
read_symbol(symbol_id)
search_code(query, limit)
find_callers(symbol_id, depth)
find_references(symbol_id, limit)
find_related_tests(symbol_id_or_query, limit)
get_agent_events(query, limit)
get_test_results()
run_project_check(kind, target?)
get_evidence(evidence_id)
```

Do **not** expose unrestricted shell execution to the model.

`run_project_check` must use an allowlisted command registry derived from known project scripts/configuration.

Supported kinds:

```text
test
build
lint
typecheck
```

For V1, target-specific test commands may be used only when they can be derived safely from existing project configuration.

The agent loop should conceptually be:

```python
for step in range(max_steps):
    response = call_haiku(messages, tools)

    if response requests tools:
        results = execute_read_only_or_allowlisted_tools(response)
        append_results(messages, results)
        continue

    verdict = parse_final_verdict(response)
    return verdict

return UNCERTAIN
```

Default budget:

```text
MAX_TOOL_STEPS_PER_REQUIREMENT=8
MAX_GRAPH_DEPTH=2
MAX_CODE_SNIPPET_LINES=120
MAX_SEARCH_RESULTS=8
```

Expose them through configuration.

# 9. Cost-Aware Reasoning

Cost efficiency is a first-class product feature.

Track per session:

```text
model input tokens
model output tokens
model calls
tool calls
files in repository
files inspected
symbols inspected
requirements checked
cache hits
estimated repository lines avoided
```

Implement caching.

At minimum cache by content hash:

```text
parsed AST
symbol extraction
file snippets
search results
requirement + evidence packet → semantic verdict
```

If the repository/evidence has not changed, do not pay for identical reasoning twice.

Never repeatedly send the entire conversation history to Haiku.

For each requirement, maintain a compact investigation state.

The UI should be able to display something like:

```text
Repository files:         842
Files inspected:           11
Symbols inspected:         18
Model input tokens:     9,840
Estimated context avoided: 90%+
```

Do not fabricate savings.

If a trustworthy denominator cannot be calculated, display raw numbers instead.

# 10. Deterministic Verification Engine

Implement rule-based checkers before semantic analysis.

Examples:

### Schema / migration protection

Detect changes to likely schema/migration paths:

```text
prisma/schema.prisma
**/migrations/**
supabase/migrations/**
*.sql
```

Only apply this rule when relevant to a requirement.

### Dependency changes

Compare:

```text
package.json
pnpm-lock.yaml
package-lock.json
yarn.lock
pyproject.toml
requirements*.txt
```

### Secret-risk scan

Look for newly introduced obvious secret patterns.

Avoid claiming every matching string is definitely a secret.

Label suspicious findings appropriately.

### Protected paths

If the Intent Contract has protected areas, map changed files against them.

### Tests

Determine whether tests were added/modified and whether relevant tests actually ran.

### Build/lint/typecheck

Run only detected project checks and record:

```text
command
exit code
duration
stdout tail
stderr tail
```

Never allow model-generated arbitrary commands.

# 11. Verdict Model

Use:

```python
class Verdict(BaseModel):
    requirement_id: str
    status: Literal[
        "VERIFIED",
        "LIKELY",
        "UNCERTAIN",
        "VIOLATED"
    ]
    evidence_level: Literal[
        "runtime",
        "test",
        "structural",
        "semantic",
        "insufficient"
    ]
    summary: str
    evidence_ids: list[str]
    missing_evidence: list[str]
    files_inspected: list[str]
    tool_calls_used: int
```

Rules:

### VERIFIED

Requires deterministic, test, or targeted runtime evidence that directly establishes the requirement.

### LIKELY

Strong semantic/structural evidence supports the requirement, but there is no conclusive runtime/deterministic proof.

### UNCERTAIN

Evidence is incomplete, conflicting, or investigation budget was exhausted.

### VIOLATED

Evidence directly contradicts the requirement.

A violation can be established by deterministic, runtime, or clear semantic code evidence.

# 12. Unexpected Change / Intent Drift Analysis

One of Cerno's highest-value outputs is identifying changes that are high-impact but weakly related to the user's stated intent.

Classify significant changes as:

```text
EXPECTED
EXPLAINABLE
UNEXPLAINED
CONTRADICTORY
```

Examples:

Developer asks:

```text
Add profile photo upload.
```

Changes:

```text
profile.tsx          EXPECTED
storage.ts           EXPECTED
package.json         EXPLAINABLE
auth/session.ts      UNEXPLAINED
schema.prisma        maybe EXPLAINABLE or CONTRADICTORY depending on intent
```

For each unexplained/contradictory change show:

```text
what changed
why it has impact
which requirement it may affect
whether Claude's session events provide an explanation
```

Do not classify merely based on filename.

Use structure + intent + agent events.

# 15. Privacy and Safety

Cerno is local-first.

The only code sent outside the machine should be the minimal evidence snippets necessary for the Anthropic reasoning call.

Before model calls:

- redact obvious API keys/tokens/secrets;
- cap snippet sizes;
- exclude `.env`;
- exclude common credential files;
- honor `.gitignore` and an `.cernoignore` file;
- never upload the entire repository.

The verification model must not have arbitrary write access.

Its tools should be read-only except for safe/allowlisted project checks.

# 20. Testing Requirements

Write real tests for the core logic.

At minimum:

### Intent compiler

- parses explicit requirements;
- does not invent excessive requirements;
- validates structured model output.

### Baseline attribution

- does not blame Claude for pre-existing dirty-tree changes.

### Git analyzer

- detects create/modify/delete;
- handles untracked files.

### Tree-sitter analyzer

- identifies changed functions/classes/imports;
- extracts source ranges.

### Graph traversal

- respects max depth;
- does not revisit cycles.

### Evidence retrieval

- prioritizes directly changed symbols;
- limits context;
- respects ignored files.

# 26. Engineering Rules

Follow these strictly.

1. **Do not overengineer.**
2. Prefer boring, inspectable Python over frameworks.
3. Keep verification logic testable without an API call.
4. Keep Anthropic integration behind an adapter.
5. Use Pydantic schemas at every AI/system boundary.
6. Never trust model output without validation.
7. Never allow Haiku arbitrary shell execution.
8. Never send entire repositories to the model by default.
9. Never fabricate a verification result.
10. Preserve evidence provenance.
11. Distinguish facts from semantic inference.
12. Do not make the UI responsible for business logic.
13. Do not hardcode demo results.
14. Do not break existing Claude Code configuration.
15. Fail open in OBSERVE mode if Cerno itself crashes.
16. Optimize for a compelling, reliable end-to-end demo before expanding feature breadth.

# Final Instruction

Build this as a **real verification agent**, not an AI-themed dashboard.

The defining behavior should be observable in the implementation:

```text
Haiku forms a verification plan
→ calls narrow repository/evidence tools
→ receives structured observations
→ decides whether more evidence is necessary
→ stops when the requirement can be defended
→ returns an evidence-backed verdict
```

The model should reason autonomously, but the surrounding algorithms must aggressively reduce irrelevant context, constrain tool access, and provide high-quality evidence.

The result should demonstrate that a lightweight reasoning model can review complex AI-generated changes efficiently **because Cerno gives it the right evidence instead of the entire codebase**.

When tradeoffs arise, optimize for:

```text
evidence quality
> correctness
> demo reliability
> context efficiency
> architectural cleanliness
> feature count
```
